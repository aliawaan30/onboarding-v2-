# Twilio Number Setup

## What this skill is for

Retell sells phone numbers in the United States and Canada only. Everywhere else,
the number comes from Twilio and gets connected to Retell over SIP. This skill
builds the Twilio side and hands one exact value to the next skill: the trunk
domain.

Get one character of that domain wrong and every transfer fails with an error
message about permissions that has nothing to do with permissions. That happened on
the live build and it cost a full day. This skill exists so it does not happen
again.

## Parameters

- `{COUNTRY}` and `{AREA_CODE}` where the client's number should look local.
- `{ACCOUNT_SID}` the Twilio Account SID.
- `{AUTH_TOKEN}` the Twilio Auth Token.
- `{TRUNK_NAME}` a name for the trunk, unique to this client.
- `{TRUNK_DOMAIN}` the trunk's SIP domain, which Twilio generates. You do not
  choose the format, you read it back exactly as shown.
- `{TWILIO_NUMBER}` the number you buy, in full international format.

## The trial account, said plainly up front

A brand new Twilio account is a trial account, and a trial account is enough to
build and test the whole thing yourself. Tell the owner this before they reach for a
credit card.

What a trial account gives you:

- One elastic SIP trunk. One is all this build needs.
- Outbound calls only to **verified** numbers. The owner verifies their own mobile
  in Twilio, and that same mobile is the transfer target while testing. It lines up
  exactly.

What it will not do:

- A second trunk. Trying returns error `21244`, "Only one trunk allowed for trial
  accounts".
- Outbound to a number that is not verified.

The upgrade happens at the first paying client, and the client's money pays for it.
Do not tell someone to upgrade before they have one.

Buying a local number in some countries also needs identity paperwork approved
first, which is a separate wait. `[VERIFY: confirm the paperwork requirement for
{COUNTRY} on Twilio's own regulatory guidelines page before promising a go-live
date.]`

## Step 1: credentials, and the five second check that saves an hour

The owner needs the **Account SID** and the **Auth Token** from the Twilio console
home page. Save both into the app's secrets.

**Use the Auth Token. Never use a scoped API key.** Scoped keys hit permission walls
on trunking and on messaging, and every wall looks like a different bug. The Auth
Token has full account access and skips all of it.

Then run this check before you make a single API call:

- An Account SID starts with `AC` and is **34 characters** long.
- An Auth Token is **32 characters** long and does not start with `AC`.

If both values start with `AC`, the same value got pasted twice, or an automatic
secret detector grabbed the wrong line. That is exactly what happened on the live
build, and every Twilio call came back with error `20003 Authenticate` while both
values looked correct on screen. Count the characters. Then make one harmless read
call and confirm it returns the account.

## Step 2: buy the number

- Search Twilio's available local numbers for `{COUNTRY}` with `{AREA_CODE}`.
- Buy one that has **Voice** capability.
- Record `{TWILIO_NUMBER}` in full international format, starting with the plus
  sign.

The number costs a few dollars a month. On a real client the Twilio account sits in
the client's business name and the client pays Twilio directly, so this line never
comes out of the owner's pocket.

## Step 3: create the elastic SIP trunk

Create an elastic SIP trunk named `{TRUNK_NAME}` and set exactly these:

- **Transfer mode: `enable-all`.** Without this, a transfer on a real call fails.
  This is not optional and it is not a default.
- **Authentication: IP access control list.** Create an IP access control list
  containing the Retell SBC block `18.98.16.120/30` and attach it to the trunk.
- **No SIP credentials.** The IP list is the whole auth story. Credentials are one
  more secret to manage, leak and rotate. Do not create any.
- **Origination URL: `sip:sip.retellai.com`**, priority 1, weight 10, enabled.
  This is the address Twilio sends incoming calls to, and it is the same for
  everyone.
- **Secure: off.**
- Caller name lookup: off.
- Recording: do not record at the trunk. Retell handles recording.

Then attach `{TWILIO_NUMBER}` to the trunk.

One consequence to know before you attach it: a number attached to a trunk ignores
every other voice setting on that number. That is fine for the overflow and
always-AI routing modes, which is what this build uses. Time-of-day routing needs a
different setup that does not go through the trunk.

## Step 4: note the trunk domain, exactly as shown

Twilio generates a SIP domain for the trunk. It looks like
`something.pstn.twilio.com`.

**Copy it exactly. Do not type it from memory. Do not shorten it. Do not tidy it
up.** On the live build the real domain ended in `-001` and the version typed into
Retell did not, and every transfer failed for a day with an error about permissions.

Read it back to the owner character by character, including any digits or hyphens,
and save it as `{TRUNK_DOMAIN}`.

## Step 5: dialling permissions

Turn on outbound voice dialling to `{COUNTRY}` in Twilio's voice geographic
permissions. Without it, the agent cannot dial out to transfer a caller, and the
failure looks like a Retell problem when it is a Twilio setting.

On a trial account, also verify the owner's own mobile as a caller ID, because
that is the only number the account is allowed to dial while testing.

## Step 6: read every value back

Print these, one per line, and compare each against the console with the owner
watching:

1. `{ACCOUNT_SID}` first four and last four characters, and its length. Should be
   34, starting `AC`.
2. Auth token length. Should be 32.
3. `{TWILIO_NUMBER}` in full international format, digit by digit.
4. The trunk name and trunk SID.
5. **`{TRUNK_DOMAIN}`, read character by character.** Then have the owner read the
   domain off the Twilio screen out loud while you compare. This one value is the
   whole reason this section exists.
6. Trunk transfer mode. Must read `enable-all`.
7. The IP access control list, and the block inside it. Must read
   `18.98.16.120/30`.
8. The origination URL. Must read `sip:sip.retellai.com`.
9. That the number is attached to the trunk.
10. That outbound dialling to `{COUNTRY}` is enabled.
11. On a trial account, that the owner's mobile shows as a verified number.

Only when all eleven read back correctly do you hand `{TRUNK_DOMAIN}` and
`{TWILIO_NUMBER}` to `retell-number-connect`.

## Things you never do

- Never create a scoped API key for this build.
- Never create SIP credentials when an IP access control list will do.
- Never retype the trunk domain from memory.
- Never tell someone to upgrade Twilio before they have a paying client.
- Never promise a go-live date before the country's identity paperwork is approved.

Once it is saved: read it, and reply "ready to set up the number" when you understand it. Do not build anything yet.

# Retell Number Connect

## What this skill is for

The Twilio side is built. This skill joins it to the voice agent, and it is the
place where one wrong character silently breaks transfers.

Read the gotcha below before you do anything else, because it changes the order you
work in.

## Parameters

- `{TWILIO_NUMBER}` in full international format, from `twilio-number-setup`.
- `{TRUNK_DOMAIN}` the trunk's SIP domain, exactly as Twilio shows it.
- `{ACCOUNT_SID}` and `{AUTH_TOKEN}` the Twilio credentials.
- `{AGENT_ID}` the published Retell agent from `receptionist-agent-builder`.
- `{INBOUND_ROUTER_URL}` the live `inbound_call_router` function URL.
- `{NICKNAME}` a name for this number in Retell, for example
  `{BUSINESS_NAME} main line`.
- `{RETELL_API_KEY}` the owner's Retell key.

## THE GOTCHA, read this first

**The Retell update-phone-number call silently ignores changes to the outbound
trunk config.** It returns success. It updates the modification timestamp. It
changes nothing.

The termination URI can only be set at import. So:

- If the termination URI is wrong, you **delete the number in Retell and import it
  again** with the correct value.
- You **never** try to fix a termination URI with an update or a patch. It will
  look like it worked and it will not have worked, and you will spend the next hour
  debugging the wrong thing.

Deleting the number in Retell does not give up the number. Twilio still owns it.
You are only removing Retell's record of it, and you rebuild that record in one
call. What you must restore after re-importing: the inbound agent, the inbound
webhook and the nickname.

## Step 1: import the number

Import `{TWILIO_NUMBER}` into Retell as **custom telephony** with:

- `termination_uri` set to **exactly `{TRUNK_DOMAIN}`**. Not a shortened version.
  Not one with a hyphen or a digit dropped. Character for character.
- Transport: **TCP**.
- The Twilio account SID and auth token, so Retell can place outbound legs.
- `nickname`: `{NICKNAME}`.

Before you send the import, print the termination URI you are about to use on its
own line and compare it to `{TRUNK_DOMAIN}` character by character. This is a ten
second check that prevents the worst bug in this whole build.

## Step 2: bind the inbound agent

Set the inbound agent on the number to `{AGENT_ID}`.

If the owner is running more than one agent version, bind the **published** one,
and check the version number, not just the name.

## Step 3: set the inbound webhook

Set the number's inbound webhook to `{INBOUND_ROUTER_URL}`.

This is what Retell calls when a call arrives, before the agent speaks, and it is
what lets the router hand the agent per-call variables.

## Step 4: read the whole config back and compare it to intent

Fetch the phone number record from Retell and print every field. Then go through
this list line by line:

1. The phone number, digit by digit against `{TWILIO_NUMBER}`.
2. **The termination URI, character by character against `{TRUNK_DOMAIN}`.** Say
   each character out loud. Do not skim it. Do not trust that it looks right.
3. Transport reads TCP.
4. The inbound agent id matches `{AGENT_ID}`, and it is the published version.
5. The inbound webhook matches `{INBOUND_ROUTER_URL}`.
6. The nickname is set.

If any of lines 1 to 3 is wrong, go to the triage tree. Do not patch it.

## The troubleshooting tree: transfer fails with a permissions error

The exact error is: `Transfer call cannot be completed, probably don't have the
permission to perform the transfer.`

Ignore the word "permission". It is almost never about permissions. Work through
these four checks **in this order** and stop at the first one that is wrong.

### Check 1: the termination URI, character by character

Fetch the number record from Retell. Fetch the trunk from Twilio. Put the
termination URI and the trunk domain next to each other and compare them one
character at a time.

This is the cause most of the time. On the live build the trunk domain ended in
`-001` and the imported termination URI did not, so every transfer was dialling a
trunk that does not exist. Nothing in the error message hinted at that.

If they do not match, go to Check 4.

### Check 2: the trunk transfer mode

Read the trunk's transfer mode from Twilio. It must be `enable-all`. If it is
anything else, set it to `enable-all` and test again. Transfers over SIP need it
and it is not on by default.

### Check 3: the IP access control list

Read the trunk's authentication. There must be an IP access control list attached
containing `18.98.16.120/30`, which is the Retell SBC block. If the trunk has no
credentials and no IP list, Twilio rejects Retell's SIP and the call goes nowhere.
Attach the list and test again.

Also confirm outbound dialling to the country is switched on in Twilio's voice
geographic permissions, and on a trial account, that the transfer target is a
verified number.

### Check 4: the termination URI is wrong, so re-import

Not a patch. A delete and re-import.

1. Read the current config and write down the inbound agent id, the inbound webhook
   URL and the nickname. You are about to lose all three.
2. Delete the number in Retell.
3. Import it again with `termination_uri` set to the **correct** `{TRUNK_DOMAIN}`,
   transport TCP.
4. Restore the inbound agent.
5. Restore the inbound webhook.
6. Restore the nickname.
7. Read the whole config back again, character by character.
8. Test the transfer on a real call, not a web call.

## Two limits that will waste your afternoon if you forget them

- **A web call can never test a transfer.** Retell's transfer only works on phone
  calls. The dashboard Test button is a web call, so it will never prove a transfer
  works no matter how many times you press it.
- **A green dashboard test is not a working phone line.** The only proof is a real
  call to the real number. See `receptionist-test-protocol`.

## Read-back verification before you say the number is connected

Print all six lines from Step 4 again, plus:

7. The trunk transfer mode, read from Twilio, showing `enable-all`.
8. The IP access control list contents, showing `18.98.16.120/30`.
9. The origination URL on the trunk, showing `sip:sip.retellai.com`.

Then hand over to `receptionist-test-protocol` and run steps 2 and 3, the real
inbound call and the transfer test.

Once it is saved: read it, and reply "ready to connect the number" when you understand it. Do not build anything yet.

# Receptionist Test Protocol

## What this skill is for

"It sounded great in the test" is not working. A build is working when all four
steps below pass, in this order, with the exact success signals written next to
them. Anything less and the owner is about to tell a client something that is not
true.

Run the whole protocol on every new build. Run it again after any change to the
agent, the phone number, the trunk or the booking backend.

## Parameters

- `{TWILIO_NUMBER}` the business line, full international format.
- `{OWN_MOBILE}` the mobile the transfer goes to, full international format. On a
  Twilio trial account this must be a verified number.
- `{AGENT_ID}` the published agent.
- `{APP_URL}` the Base44 app, for checking the Booking entity.

## Step 1: the dashboard web call

Open the Retell dashboard and press the Test button to talk to the agent in the
browser.

What you are testing: does it hold a conversation, does the booking flow work, do
the tools actually fire.

Run a full booking out loud. Give a name, a phone number, an address, say what you
need, and ask for tomorrow. Listen for:

- It asks one question at a time. If it interrogates you with three at once, the
  role prompt is too long or the facts are in the prompt instead of the knowledge
  base.
- It quotes prices that match the client's website. If it invents one, the
  knowledge base is wrong or missing.
- It offers real times, and the date it reads back is genuinely tomorrow. If it
  says a date from a different year, the date rule is not in the tool descriptions.

**Success signal:** the conversation feels normal, and both tool calls show as
executed in the call detail, not failed.

**What this step can NEVER test:** the transfer. Retell's transfer works on phone
calls only. The dashboard Test button is a web call. Pressing it a hundred times
proves nothing about transfers.

Two practical notes:

- **Use a decent microphone**, especially for a client demo. On a noisy laptop mic
  the speech recognition mangles words. On the live build "callout fee" came
  through as "full outfit".
- **Never host a custom web-call test page on a Base44 function.** Base44 functions
  serve HTML with a content security policy that blocks all scripts, so the page is
  dead in the browser, and Retell refuses web calls from a local file. Use the
  dashboard, or host the page on a real site outside Base44 functions.

## Step 2: the real inbound call

Ring `{TWILIO_NUMBER}` from your own phone.

Run a full booking again, properly, as if you were a customer.

**Success signals, all three:**

1. The agent picks up with the right business greeting.
2. A new row appears in the Booking entity in the app, with the right name, phone,
   address, date and time. Check the date is real, not two years ago.
3. The call events show up from the webhook: call started, call ended, and the
   post-call analysis.

If the conversation was fine but no row appeared, the tool URLs are wrong. Read
them back off the LLM object character by character against the live function URL.

## Step 3: the transfer test

This is the step that gets skipped and it is the one that fails on real clients.

Two ways to run it. Either works.

**Option A, the simple one.** Ring `{TWILIO_NUMBER}`, and part way through say
"can you put me through to a human".

**Option B, placed by API.** Create a phone call through Retell with the business
number as the from number, `{OWN_MOBILE}` as the to number, and `{AGENT_ID}` as the
agent override. Then ask for a human on that call.

**Success signal, and it has two halves. Both must happen:**

1. The call ends with a disconnection reason of `call_transfer`.
2. **Your own mobile rings.**

If the call ends with `call_transfer` but nothing rings, it is not working. If you
hear the error "Transfer call cannot be completed, probably don't have the
permission to perform the transfer", that is almost never about permissions. Go to
the troubleshooting tree in `retell-number-connect` and work the four checks in
order, starting with the termination URI character by character.

## Step 4: check the records after every call

After each test call, open the app and Retell and confirm:

- The Booking row exists and every field is right, especially the date.
- The post-call analysis fields are populated: caller name, what they wanted,
  whether a booking was made.
- The call transcript reads like a conversation a customer would be happy with.

Then delete the test bookings so the client's data starts clean.

## What "working" means, in one line

The agent answered a real call on the real number, a real booking row exists with
the right date, and asking for a human made a real mobile ring. Until all three of
those have happened, the build is not finished, whatever the dashboard says.

## Read-back verification

Print a short pass or fail line for each of the four steps, with the actual
evidence next to it: the greeting you heard, the booking row id, the disconnection
reason, and whether the mobile rang. If any line is a fail, say so plainly and name
which skill fixes it. Do not report a build as ready with a fail on the sheet.

Once it is saved: read it, and reply "ready to test" when you understand it. Do not build anything yet.

# Receptionist Client Intake

## What this skill is for

Every client already has a phone number. That number stays theirs. Your job is to
get their unanswered calls to reach the AI without breaking anything they rely on.

There are several ways that can work depending on what kind of phone they have and
when they want the AI to pick up. Guessing wastes days and can take a business
offline. This skill asks the right questions first, then writes a plan the owner
can follow without thinking.

## The rules you follow

1. **Never guess.** If you do not know something, write "check this with the owner"
   or "test this before go-live". Never state as fact something you were not told
   and that is not in this skill.
2. **Plain language.** Write so a twelve year old could follow it. Say "the phone
   company", not "the carrier", wherever you can.
3. **One job per step.** Every step has one action and one person doing it.
4. **Say who does it.** Tag every step YOU (the owner running the agency), CLIENT
   (the business owner), or ME (this agent).
5. **Never ring the client's business number back.** See the loop trap. This is the
   fastest way to break a client's phones.
6. **No em-dashes in anything you write.**

## Part 1: the interview

Ask these in order, one or two at a time, in normal conversation. Do not move on
without an answer. If the owner does not know, that becomes a question for the
client and you say so.

### Q1. Which country is the client in?

Why it matters: it decides where the number comes from, whether identity paperwork
is needed, and what the forwarding code is.

- United States or Canada: Retell sells the number directly. No Twilio needed.
- Australia, New Zealand, United Kingdom and much of Europe: the number comes from
  Twilio and gets imported into Retell. Identity paperwork usually has to be
  approved first, which takes days, not hours.
- Anywhere else: say plainly "I have not been given the rules for that country. Do
  not promise the client a date until we check what Twilio needs there."

### Q2. What is the business number, and what kind of phone is it?

Read the four options out and let them pick:

- **A. A mobile.** The business number is a phone in someone's pocket.
- **B. A landline or internet phone.** A fixed line at a shop or office, usually a
  handset on a desk, often bundled with the internet.
- **C. A phone system.** More than one handset, or extensions, or someone who
  transfers calls. Names to listen for: 3CX, RingCentral, Aircall, Zoom Phone,
  Microsoft Teams Phone, "our VoIP system", "our PBX".
- **D. They do not know.**

If the answer is D, give the owner these exact words to send the client:

> Quick one so I can set your AI up properly.
> 1. Is your business number a mobile you carry, or a phone sitting at the shop?
> 2. Who do you pay for it each month?
> 3. Does anyone else's phone ring when that number is called?
> 4. When you miss a call now, what happens? Voicemail, or does it ring someone
>    else?

Map the answers: mobile they carry equals A. One handset at the shop, nobody else
rings, equals B. Anyone else rings, or extensions, or a system named, equals C.
Still unclear means ask them to log in wherever they pay the bill and read out what
the service is called. Do not proceed on a guess.

### Q3. Which phone company?

You need the company name to give them the right forwarding code and to know
whether forwarding is even available on their plan.

### Q4. When should the AI pick up? The five modes.

Read these out in plain words and let them choose one.

- **Overflow.** Their phone rings first, like normal. If nobody answers after about
  twenty seconds, the AI takes it. Outside hours it goes straight to the AI. This
  is what most people want and it is the simplest to build.
- **After hours only.** In business hours they answer everything and the AI never
  touches a call. Outside those hours the AI takes everything.
- **Always AI first.** Every call goes to the AI, every time. It handles bookings
  and questions and passes real humans through.
- **AI as backup, with transfer.** Overflow, but the AI also offers to put urgent
  callers through to their mobile.
- **Split by intent.** The AI answers everything, handles the simple calls, and
  passes anything complicated to a human.

These are routing settings, not different agents. The same agent works for all
five. What changes is where the calls come from before they reach the AI.

Recommend Overflow unless they have a reason. It needs one code tapped into one
phone and there is nothing else to break. After hours and Split need a piece of
routing that decides call by call, which is more to build and more to test.

If they choose anything other than Overflow, ask their exact business hours and
which days.

### Q5. What mobile should the AI ring when a caller needs a human?

This must be a **different number from the business number**. Get it in full
international format and read it back digit by digit.

If the owner is still on a Twilio trial account, that mobile has to be verified in
Twilio before the AI can dial it. Do that now, not on the day you go live.

If the client only has one phone, say it plainly:

> Because your business number sends missed calls to the AI, the AI cannot ring
> that same number back or the call goes in a circle. Two options. Either we keep
> it simple and the AI takes a message every time, or you give me a second number
> to reach you on.

### Q6. THE LOOP TRAP CHECK. Ask this directly, every single time.

Ask the client, in these words:

> On the mobile you want the AI to transfer calls to, is there any call forwarding
> switched on right now? Anything that sends calls somewhere else, always or when
> you miss them?

Why this question exists: if the transfer mobile has **unconditional forwarding**
pointing back at the AI number, the AI transfers a caller, the caller lands on the
mobile, the mobile immediately forwards them back to the AI, and round it goes. The
client's phones effectively stop working.

The rule: the transfer mobile must have **no forwarding, or conditional forwarding
only** (forward when not answered, or when busy). Never unconditional.

**Never infer forwarding from call data.** On the live build a diversion marker in
the call information led to a wrong conclusion that the owner had forwarding set up
when he had never touched it. Ask the person. Believe the person. If they are not
sure, have them check with the code in the table below and read the result back to
you.

### Q7. What happens when the AI takes a booking? The booking situation.

Three tiers. Find out which one this client is.

- **Tier 1, the default that always works.** The AI takes all the details and they
  land in the app as a booking record. The owner sees them in the app, or asks
  their co-founder agent for the day's bookings. This works for every business on
  earth, needs nothing from the client, and is what you sell. Most trades are here,
  running on a diary or a whiteboard.
- **Tier 2, Google Calendar.** The client already lives in Google Calendar and
  wants real-time availability and real bookings in it. Possible, needs a bridge
  built and a Google login connected. Only offer it if they already use Google
  Calendar as their actual calendar.
- **Tier 3, their booking platform.** Some platforms let other software book into
  them directly. More work, higher price, and only worth it for a client whose
  whole business runs through one.

The honest script when a client has an unusual system:

> We work with all sorts of systems. Either we connect straight to yours, or the AI
> qualifies the caller and takes the full booking, which lands in one place you
> check. During setup we test your exact workflow. If we cannot make it seamless,
> you do not pay.

Do not promise a text message to the caller or to staff. That needs paperwork on
the phone number that is not in place yet. `[VERIFY: SMS is blocked pending the
Twilio regulatory bundle and messaging permission. It is the first upgrade, not
part of the first build.]`

### Q8. Who is the emergency contact, and what counts as an emergency?

For a trade, a burst pipe at 11pm is not the same call as a quote request. Get the
number, and get the client's own words for what counts.

### Q9. What should the AI never say?

Prices they do not want quoted. Timeframes they cannot hold to. Anything about
warranties, insurance or someone else's work. Write it down word for word. It goes
straight into the agent's guardrails.

### Q10. Whose name is the phone account in?

The normal answer is that the Twilio account sits in the client's business name and
the client pays Twilio directly, and the owner has the login and manages it. That
keeps the number portable and keeps the owner out of the billing.

## Part 2: the decision tree

Work through this in order. Do not skip ahead and do not invent a branch.

### Branch 1: the country

```
United States or Canada?
  YES -> Retell sells the number directly. No Twilio, no paperwork.
         Buy the number in Retell, bind the agent, then go to Branch 2.
  NO  -> You need a Twilio number. Continue.

Australia, New Zealand, United Kingdom or Europe?
  YES -> Twilio sells numbers there, and each one needs identity paperwork
         approved before you can buy it. Once one bundle is approved it covers
         every future number of the same type in the same country.
         If the paperwork is already approved: the number can be live today.
         If it is not: tell the client "later this week", never "this afternoon".
  NO  -> Stop. Tell the owner you have not been given the rules for that country.
```

### Branch 2: where the client's number lives

```
A. A MOBILE on a normal mobile company
   -> Nothing to build. The CLIENT taps one code into their own phone, once.
      Twenty seconds. Go to the forwarding codes below.

B. A LANDLINE or INTERNET PHONE
   -> Codes usually do not work. Forwarding is a setting on the phone company's
      website. The CLIENT logs in, or adds YOU as a user.
      Ask: "Can you log in to your phone service online? Who do you pay?"
      Then say honestly: "I do not know that provider's exact menu. Get on a
      screen share and look for Call Forward, Divert or Follow Me. The setting
      you want is forward when not answered, pointing at the new number."
      The usual hold-up is that nobody knows the login. Ask for it a day early.

C. A PHONE SYSTEM (3CX, RingCentral, Aircall, Teams Phone and similar)
   -> Someone already looks after it. YOU do not touch it. Tell their phone
      person what you need. Give the owner this to send:
        "Hi, we are adding an AI receptionist. Can you add a forward rule so that
        when a call is not answered after about twenty seconds it goes to
        {TWILIO_NUMBER}? Please leave everything else as it is."
      Ask what happens today first. These systems often already overflow to
      somebody's mobile, and you do not want two hops.

D. THEY ASK TO MOVE THE NUMBER TO TWILIO
   -> Say no, and say why: "We do not need to move your number. We just point
      missed calls at the new one. Moving it takes weeks, needs signed forms,
      and if anything goes wrong your phone stops working."

E. SOMEONE SUGGESTS HOSTED NUMBERS
   -> They do not do voice calls. Do not offer it for a receptionist.
```

### Branch 3: how the AI gets the call once it reaches Twilio

```
Overflow or Always AI?
  -> Simplest setup. The Twilio number sits on the SIP trunk pointing at Retell,
     and the number is imported into Retell. Nothing else. Recommend this.

After hours or Split by intent?
  -> The simple setup cannot do this. A number attached to a trunk ignores every
     other setting on that number, so there is nowhere to put a clock.
     For these two the number does NOT go on the trunk. It points at a small piece
     of routing that decides, call by call, whether to ring a human or hand the
     call to the AI. Build that routing, then test it with real calls before you
     tell the client it is live.
     [VERIFY: the routing function path has not been proven end to end on a real
     call in this build.]
```

## The forwarding codes

These are the codes the CLIENT taps into their own mobile. They are a phone network
standard rather than a Twilio feature, and the same codes are used across
Australian, New Zealand and UK mobile networks.

| What you want | Code to tap | Undo it | Check it |
|---|---|---|---|
| Forward only when they do not answer | `**61*NUMBER#` | `##61#` | `*#61#` |
| Same, choosing how long it rings first | `**61*NUMBER**SECONDS#` | `##61#` | `*#61#` |
| Forward every call, always | `**21*NUMBER#` | `##21#` | `*#21#` |
| Forward when the line is busy | `**67*NUMBER#` | `##67#` | `*#67#` |
| Forward when the phone is off | `**62*NUMBER#` | `##62#` | `*#62#` |
| Undo everything, the panic button | `##002#` | | |

**Confirm the exact code on the client's own phone company support page before you
send it.** Companies change these and some plans do not allow forwarding at all.
United States carriers use different codes again, so look theirs up rather than
using this table. `[VERIFY: these codes have not been live-tested on every
network.]`

Ring time: five to thirty seconds, in steps of five. Roughly five seconds is one
ring. About twenty-five seconds, which is five rings, is the good default.

Always write the number in full international format starting with the plus sign.

### The two 61s that confuse everyone

An Australian code looks like this:

```
**61*+61XXXXXXXXX**25#
```

Two 61s, and they mean completely different things.

- The **first 61**, right after the two stars, is the phone network's code for
  "when I do not answer". It is the same in Australia, New Zealand and the UK and
  has nothing to do with Australia.
- The **second 61**, after the plus sign, is Australia's country code. It is part
  of the phone number.

Say this out loud to the client so they do not think they typed it twice. It looks
like a typo and it is not.

### If the code does not work

- Some phone companies want you to use the phone's own menu instead: Phone app,
  then Settings, then Call forwarding, then "when unanswered", then the number.
- Some prepaid plans cannot forward at all. Check whether they are on prepaid.
- If nothing works, have them tap `##002#` to clear everything and start again.

### The cost question, answered honestly

The client's phone company may charge them for the forwarded leg, as if they had
made that call themselves. On some plans it is free. Say this word for word:

> Your phone company might charge you for the diverted leg like a call you made
> yourself. On a lot of plans it is included. Have a quick look at whether your
> plan has unlimited standard calls. If it does, you will not notice it.

Never promise it is free.

## The voicemail trap

This one comes free with every setup that rings a human.

You ring the owner's mobile to pass a caller through. The owner does not pick up.
Voicemail does. Voicemail counts as someone answering, so the caller gets connected
to a beep and a greeting instead of getting help, everyone hangs up, and from the
outside it looks like it worked.

The fix, built into the routing: before connecting the caller, the system whispers
privately to the owner, "New call for your business, press 1 to take it."
Voicemail cannot press 1. If nothing is pressed within a few seconds, that leg is
dropped and the caller goes to the AI instead. The caller hears normal ringing the
whole time and never knows.

Include this in the plan every time the setup rings a human.

## Part 3: write the plan

Output exactly these seven sections, in this order, with these headings. Nothing
else. Plain language throughout.

### 1. What we are doing, in one paragraph

Two or three sentences. Name the client, say their number stays where it is, say
what happens when they miss a call, and say when the AI picks up.

### 2. The steps

A numbered list. Every step tagged YOU, CLIENT or ME, one action each. The shape:

```
1. YOU: Get the identity paperwork approved on the Twilio account. One time job,
   covers every client after this.
2. ME: Buy the number and build the trunk.
3. ME: Connect the number to Retell and put this client's agent on it.
4. YOU: Ring the new number yourself. Confirm the AI answers.
5. CLIENT: On the business phone, tap the forwarding code and press call.
6. YOU: Ring the business number from a different phone, let it ring out, confirm
   the AI answers.
```

### 3. The exact code or setting

The literal string to tap, or the literal path through the menu, written so it can
be pasted into a text message to the client. Add the two 61s explanation if it is
one of those codes. Add the line telling them to confirm it on their phone
company's own support page.

### 4. What it costs to run

The number is a few dollars a month. The voice is charged per minute of call time.
Give the owner the real current figures from Retell and Twilio, say plainly which
currency they are in, and never quote what the client's own phone company charges
for a diverted call.

### 5. Who does what, at a glance

Three short lists: YOU, CLIENT, ME. Headlines only. This is what the owner forwards
to the client.

### 6. Test before you tell the client it is live

Always include these, in this order:

```
1. Ring the new number from your own phone. The AI answers.
2. Ring the client's business number from a phone that is not theirs. Let it ring
   right out. The AI picks up.
3. Ring in and book something. Check the booking appears in the app with the right
   date.
4. Ring the business number and have the CLIENT answer it. Confirm the AI stays out
   of the way and nothing sounds different.
5. Ring in and ask for a human. The call must end as a transfer AND the owner's
   mobile must actually ring.
6. If a human is in the routing: let their voicemail pick up. The caller must end
   up with the AI, not with voicemail.
7. Have the client tap the check code on their phone. It should read back the new
   number.
```

The full detail of steps 1, 3 and 5 lives in `receptionist-test-protocol`. Run that
skill, do not rewrite it here.

### 7. If it goes wrong

Always include these four:

```
- Client wants everything back to normal right now: they tap ##002# and press
  call. Every divert clears in one second and their phone works exactly as before.
  Tell them this line at the start. It takes all the fear out of it.
- The AI never picks up: check the divert is actually on with the check code, then
  ring the new number directly to find out whether the problem is the divert or
  the AI.
- Callers hear an error message: the routing did not answer in time. There should
  be a backup on the number that takes a message instead.
- The AI cannot ring the owner out: outbound dialling to that country is switched
  off in Twilio. Turn it on in voice geographic permissions.
```

## Read-back verification

Before you hand the plan over, print and confirm with the owner:

1. Country, phone company, and phone type.
2. The chosen routing mode, in the client's own words.
3. The business hours, if the mode needs them.
4. The transfer mobile, digit by digit, and confirmation that it is NOT the
   business number.
5. The loop trap answer, in the client's own words, and confirmation that any
   forwarding on the transfer mobile is conditional or absent.
6. The booking tier.
7. The emergency contact.
8. The never-say list, word for word.

## Things you never do

- Never tell a client to move their number in order to get started.
- Never ring the client's business number from the routing.
- Never promise the client their phone company will not charge them.
- Never promise a same-day go-live before the identity paperwork is approved.
- Never promise a text message to the caller or to staff in the first build.
- Never put a number on a SIP trunk and then promise time-of-day routing on it.
- Never assume what forwarding a client has. Ask them.
- Never use an em-dash.

For the day you land a client

When you land your first client, these two are waiting for you. Neither one is part of your own build, so skip them today and come back the day someone says yes.
One role. Administrator. That is the whole answer.
In the video Blake lists a few extra roles and second-guesses himself on camera. Ignore that part. The client creates the account so they stay the Owner, they invite you as a user, and they give you Administrator. That lets you buy numbers, build the trunk, create API keys, submit regulatory bundles and read the logs. It does not let you close the account or remove them, which is exactly what they should keep. Skip Messaging Insights and Voice Intelligence, they are analytics roles and this build does not touch them. If a client would rather keep you out of billing, Developer works instead.

US and Canadian clients need no paperwork at all. Numbers there are instant. Almost everywhere else, and that means every Australian client, needs what Twilio calls a regulatory bundle.

Here is the part that saves your launch. In Australia you can buy a local number and take calls straight away with just an Australian address on file. The bundle is what unlocks text messages, not calls. So your receptionist can be answering the phone the same day, while the bundle approves in the background. Start it the day they say yes anyway, because approval takes 24 to 48 hours.

What Australia asks for. A registered business needs four things: an ASIC company extract, proof of the business address, photo ID for the person you list as the representative, and, only if that person is not a director on the extract, a letter of authorisation signed by one who is. A sole trader needs two: photo ID and one document showing their address. It has to be a street address, Twilio rejects PO boxes.
